# Metal traces of the Q4_0 matmul for 8 rows

Recorded 2026-11-18 on an Apple M4 Pro, macOS 27.2.1, with
`xctrace record --template 'Metal System Trace'`. One shape: `down` of
Qwen2.5-0.5B (N = 896, K = 4,864), Q4_0, M = 8, `cold` mode, 5 samples of
256 ops after 10 warm-up samples (3,840 ops in each trace). The timers are
the ones of `bench/runs/2026-11-17-6996c8f-matmul.md`, at `28db357` with
the shape filters (`FORNACE_OP_COST_OPS` and the others, `--ops` and the
others) added. The `.trace` files are not in the repository (about 1 GB).

## Commands

Candle, from `crates/fornace-engine` (`<layout>` is `m_axis` or
`batch_axis`; for #3898, the test binary of the #3898 worktree):

```sh
xctrace record --no-prompt --template 'Metal System Trace' --output candle.trace \
    --env FORNACE_OP_COST_MODELS=0.5b --env FORNACE_OP_COST_OPS=down \
    --env FORNACE_OP_COST_FORMATS=q4_0 --env FORNACE_OP_COST_ROWS=8 \
    --env FORNACE_OP_COST_MODES=cold --env FORNACE_OP_COST_SAMPLES=5 \
    --env FORNACE_OP_COST_LAYOUTS=<layout> \
    --launch -- <test binary of matmul_op_cost> --ignored --nocapture --test-threads=1
```

ggml:

```sh
xctrace record --no-prompt --template 'Metal System Trace' --output ggml.trace \
    --launch -- ~/.cache/fornace/ref/ggml_matmul_cost --models 0.5b --ops down \
    --formats q4_0 --rows 8 --modes cold --samples 5
```

GPU busy time: the sum of the `metal-gpu-intervals` of the process at
depth 0, with overlaps merged, divided by 3,840 ops.

## Results

| Path | Op time under the tracer, µs | Step 1 op time, µs | GPU busy / span | GPU time for each op, µs | Threadgroups for each op (from the source) | Weight reads for each op |
|---|---:|---:|---:|---:|---:|---:|
| Candle `mm` (`[8, K]`) | 149.9 | 152.1 | 97 % | 150.7 | ⌈8/32⌉ × ⌈896/64⌉ = 14 | 1, in 152 steps of K = 32 for each threadgroup |
| Candle per row (`[8, 1, K]`) | 90.3 | 94.7 | 96 % | 92.6 | 8 launches of 896/8 = 112 | 8 |
| Candle with #3898 (`[8, 1, K]`) | 53.5 | 53.0 | 95 % | 55.5 | 1 launch of 112 × 8 = 896 | 8 (some from the GPU cache) |
| ggml `mul_mv_mma` (corrected, see below) | 18.1 | 22.5 | 61 % | 20.3 | ⌈896/8⌉ × ⌈8/8⌉ = 112, of 512 threads | 1 (one 8-row tile for all 8 rows) |

- In the three Candle paths, the GPU is busy 95 to 97 % of the run, and
  the GPU time for each op is the op time. So the cost is GPU work, not
  the CPU cost of a launch.
- The ggml GPU span includes the setup of the graphs, so its busy
  percentage is lower. Its GPU time for each op agrees with its op time.
- This trace template records no shader counters (only "RT Unit Active"),
  so the occupancy and the read bandwidth of each kernel are not measured.
  The threadgroup counts come from the dispatch code, not from the trace.

## Correction (2026-11-18)

The first version of this file named the ggml kernel `mul_mv_ext`, with
224 threadgroups and 2 weight reads. That was wrong. For Q4_0 and Q8_0
with 2 to 16 rows, llama.cpp b12110 uses `kernel_mul_mv_mma`
(`ggml/src/ggml-metal/ggml-metal-common.cpp:143`, the fewest rows is 2 for
these types at `:121`; the kernel is in `kernels/mul_mv_mma.metal`). The
pipeline for this shape is `kernel_mul_mv_mma_q4_0_f32_nt1_rt1` with 16
SIMD groups and `ne00=4864` (the log of `ggml_matmul_cost`). It puts up to
8 rows in one 8 × 8 simdgroup-matrix tile, takes 8 weight rows in each
threadgroup (`nt1`), and splits K over the 16 SIMD groups. Other shapes get
other tilings: gate_up `nt4` (32 weight rows) with 16 SIMD groups, and
`lm_head` `nt4` with 8 SIMD groups. The grid is at `ggml-metal-ops.cpp:2649`. The
times in the table are not changed: the timer ran this kernel.
